Wasp User Guide

User Guide

Wasp gives you sandboxed Linux VM workspaces on your Mac. Each workspace is an isolated ARM64 Linux virtual machine with its own disk, SSH access, and terminal tabs — ready for AI coding agents or manual development.

This guide starts simple and introduces features one at a time. By the end you’ll know how to use both the GUI app and the CLI.

Prerequisites

  • macOS 15 (Sequoia) or later
  • Apple Silicon Mac (M1 or later)
  • A golden disk image (see Understanding Images)

Wasp uses Apple’s Virtualization.framework, which requires Apple Silicon and the com.apple.security.virtualization entitlement.

Installing Wasp

Build from source:

git clone https://github.com/jonmagic/wasp.git
cd wasp
swift build -c release

The CLI binary is at .build/release/wasp. The GUI app can be run via Xcode (generate the project first with xcodegen generate) or directly with swift run WaspApp.

Quick Start: Your First Workspace (GUI)

This section walks you through creating your first workspace using the GUI app. Here is the overall flow — the blue steps are yours, the orange steps happen automatically:

Step 1: Prepare a Golden Image

Before you can create workspaces, you need a golden image — a pre-configured Linux disk image with SSH enabled. Use the CLI to pull and build one:

# Download the base Debian 13 ARM64 image (~640 MB)
wasp image pull

# List images to confirm the download
wasp image list

Note: wasp image build (which provisions the golden image from the base) is not yet implemented in the CLI. For now, build golden images using the wasp ssh command to boot a VM, configure it manually, then use the GUI’s “Bake Image” feature to save it. See Baking Custom Images.

Step 2: Launch the App

swift run WaspApp
# or open via Xcode

Quick Start: One-Command SSH (CLI)

If you just want a quick disposable Linux shell, the CLI has a single command that does everything:

wasp ssh

This runs the entire sequence automatically:

Behind the scenes, wasp ssh: 1. Clones the golden image to a temporary working copy 2. Generates an ephemeral SSH keypair 3. Boots the VM 4. Provisions the SSH key via the serial console 5. Sets up a vsock relay 6. Launches ssh connected to the VM

You get dropped into a root shell. When you exit (Ctrl+D or exit), the VM stops and all temporary files are cleaned up. Nothing persists.

Running a Command Instead of a Shell

You can pass a command to execute non-interactively:

wasp ssh -- uname -a
# Linux debian 6.x aarch64 GNU/Linux

wasp ssh -- cat /etc/os-release
# PRETTY_NAME="Debian GNU/Linux trixie/sid"

Customizing the Ephemeral VM

wasp ssh --cpus 8 --memory 32          # More resources
wasp ssh --image my-custom.raw         # Different golden image
wasp ssh --name my-session             # Named session (for key reuse)

Understanding Images

Wasp uses a layered image system. Understanding this will help you work efficiently with workspaces.

Image Types

Image Type What It Is Location
Base image A raw Linux cloud image downloaded from the internet ~/.wasp/images/base/
Golden image A base image that has been booted and provisioned (SSH configured, packages installed) ~/.wasp/images/golden/
Workspace image A clone of a golden image, owned by a single workspace. All changes stay here. ~/.wasp/workspaces/<name>/

Key Concepts

  • Workspaces are isolated. Each workspace has its own disk image cloned from the golden image. Installing packages in one workspace doesn’t affect others.

  • Golden images are templates. They save you from re-provisioning every time you create a workspace. Set one up the way you like it, bake it, and create workspaces from it instantly.

  • Manifests track lineage. Each golden image has a manifest recording which base image it was built from, the provision script hash, and a creation date. This lets Wasp detect when a golden image is stale.

Managing Images (CLI)

# List all images and manifests
wasp image list

# Pull the default Debian 13 ARM64 base image
wasp image pull

# Pull a specific image
wasp image pull --url https://example.com/custom.raw --filename custom.raw

# Pull with checksum verification
wasp image pull --checksum abc123...

# Clean stale golden images (based on provision script changes)
wasp image clean

# Remove all images
wasp image clean --all

Starting and Stopping

You can start or stop workspaces in three ways: 1. Context menu — right-click in the sidebar 2. Toolbar button — the play/stop button in the detail view’s status area 3. Command palette — type >start or >stop (see below)

When you start a workspace, Wasp boots the VM, provisions SSH access, and opens a serial console tab automatically. When you stop, all tabs are closed and the VM shuts down.

Working with the CLI

The CLI provides workspace management and quick-access VM commands.

Workspace Management

# Create a workspace (does not start it)
wasp workspace create my-project
wasp workspace create my-project --cpus 8 --memory 32
wasp workspace create my-project --image custom-golden.raw

# List all workspaces
wasp workspace list

# Destroy a workspace (removes all files)
wasp workspace destroy my-project

Example wasp workspace list output:

NAME         STATUS    CPUS  MEMORY
my-project   stopped      4   16GB
test-env     stopped      2    8GB

Note: wasp workspace start, wasp workspace stop, and wasp workspace forward are not yet implemented in the CLI. Use the GUI app for these operations.

Raw Boot (Advanced)

For low-level debugging, you can boot any disk image directly with serial console access:

wasp boot path/to/image.raw
wasp boot path/to/image.raw --cpus 2 --memory 8

This gives you a raw serial console (your terminal enters raw mode). The VM’s serial output appears directly in your terminal. Press Ctrl+C to stop.

This is useful for: - Debugging boot issues - Working with images that don’t have SSH configured - Low-level guest OS troubleshooting

Tabs: Terminal, Serial, and Browser

Each workspace can have multiple tabs. Tabs persist across tab switches thanks to a ZStack rendering trick — switching tabs doesn’t kill SSH connections or lose scrollback history.

Tab Types

Tab Icon What It Does
Serial 🔌 Direct serial console to the VM. Auto-created when a workspace starts. Cannot be closed.
Terminal ⌨ SSH session into the VM. Opens a new ssh process each time.
Browser 🌐 In-app web browser (WKWebView). Useful with port forwarding.

Serial Console Tab

The serial console tab appears automatically when a workspace starts. It shows the raw serial output from the VM — boot messages, kernel output, and a login prompt.

During the Starting phase, the serial console shows “Provisioning…” because the provisioner is using the serial port exclusively to inject the SSH key. Once provisioning completes and the workspace reaches the Running state, the serial console becomes interactive.

The serial console tab cannot be closed — it always stays at the first position. This ensures you always have a fallback way to interact with the VM if SSH isn’t working.

Terminal Tabs

Press ⌘T to open a new terminal tab. Each terminal tab spawns a fresh SSH session to the VM. You can have as many as you want.

Terminal tabs have automatic retry — if the SSH connection fails (which can happen briefly after boot), the tab will retry up to 10 times with 1-second delays before giving up.

Terminal tabs can be: - Renamed — right-click the tab and choose “Rename Tab…” - Closed — click the X button or press ⌘W - Reordered — drag and drop tabs in the tab bar

Browser Tabs

Press ⇧⌘T to open a new browser tab. A sheet asks for the URL:

Port Forwarding

Port forwarding lets you access services running inside the VM (like a web server) from your Mac’s browser or other tools.

Adding a Port Forward

Click the 🔌 (network icon) button in the tab bar to open the port forward popover:

┌────────────────────────────────────┐
│  Port Forwards                     │
│                                    │
│  Guest Port: [3000]                │
│  Host Port:  [3000]                │
│                                    │
│  [Add]                             │
│                                    │
│  Active Forwards:                  │
│  3000 → 3000   [Open] [Remove]    │
│  8080 → 8080   [Open] [Remove]    │
│                                    │
└────────────────────────────────────┘

Enter the guest port (the port your app listens on inside the VM) and the host port (the port to expose on your Mac). Click Add.

The port forward badge on the network icon shows the count of active forwards.

Opening in a Browser Tab

Each active port forward has an Open button that opens the forwarded service in an in-app browser tab. This is convenient for web development — you can see your app alongside your terminal without leaving Wasp.

How It Works

Port forwarding uses the same vsock transport as SSH — no TCP networking is needed between host and guest. A PortForwarder listens on the host port and relays traffic through the virtio socket to the guest port.

Port forward configurations are persisted to the workspace’s config file, so they survive app restarts.

Baking Custom Images

Once you’ve customized a workspace (installed packages, configured tools, etc.), you can “bake” it into a new golden image so all future workspaces start with those customizations.

Requirements

  • The workspace must be stopped before baking
  • You choose a name for the new golden image

Baking via the GUI

  1. Stop the workspace
  2. Right-click the workspace in the sidebar
  3. Choose Bake Image…
  4. Enter a name for the golden image (e.g., my-dev-env.raw)
  5. Click Bake
┌──────────────────────────────────────┐
│          Bake Image                  │
│                                      │
│  Workspace: my-project               │
│                                      │
│  Image name: [my-dev-env.raw      ]  │
│                                      │
│  [Cancel]                    [Bake]  │
└──────────────────────────────────────┘

The workspace’s disk image is copied into ~/.wasp/images/golden/. You can now create new workspaces using this image — they’ll start with all your customizations pre-installed.

Typical Workflow

  1. Create a workspace from the default golden image
  2. Start it and install your tools (apt install, pip install, etc.)
  3. Stop the workspace
  4. Bake it as a golden image
  5. Create new workspaces from your custom image

This is Wasp’s equivalent of building a custom Docker image — except it’s a full VM with real kernel isolation.

Managing Multiple Workspaces

You can run multiple workspaces simultaneously. Each workspace has its own: - Disk image (isolated filesystem) - SSH keypair - Set of tabs - Port forwards - VM resources (CPU, memory)

Switching Between Workspaces

Click a workspace in the sidebar to switch to it. All your tabs for that workspace are preserved — terminal sessions stay alive, scrollback history is maintained, and browser tabs keep their state.

This works because Wasp keeps all workspace detail views alive in a ZStack (not just the selected one). Switching workspaces changes which view is visible, not which views exist.

Deleting a Workspace

A workspace must be stopped before it can be deleted. Then: - Right-click in sidebar → Delete Workspace… - Or press ⌘⌫ - Or use the command palette → “Delete Workspace”

A confirmation dialog appears. Deletion removes the workspace directory, disk image, and SSH keys permanently.

File Locations

Wasp stores all its data under ~/.wasp/:

~/.wasp/
├── images/
│   ├── base/               # Downloaded base images
│   │   └── debian-13-nocloud-arm64.raw
│   ├── golden/             # Provisioned golden images
│   │   └── debian-13-sshd.raw
│   └── manifests/          # Image build metadata (JSON)
│       └── default.json
├── workspaces/
│   ├── .keys/              # SSH keypairs for all workspaces
│   │   ├── my-project      # Private key
│   │   └── my-project.pub  # Public key
│   ├── my-project/
│   │   ├── config.json     # Workspace configuration
│   │   └── debian-13-sshd.raw  # Workspace disk image (clone)
│   └── test-env/
│       ├── config.json
│       └── debian-13-sshd.raw
└── keys/                   # SSH keys for ephemeral VMs (wasp ssh)

Config File Format

Each workspace has a config.json:

{
  "name": "my-project",
  "cpuCount": 4,
  "memoryGB": 16,
  "sshKeyName": "my-project",
  "goldenImageFilename": "debian-13-sshd.raw",
  "portMappings": [
    {"guestPort": 3000, "hostPort": 3000}
  ]
}

Troubleshooting

“No images available” when creating a workspace

You need a golden image first. Pull a base image and prepare it:

wasp image pull
wasp image list  # Verify it downloaded

Then either build a golden image manually (boot with wasp ssh, configure, bake from the GUI) or place a pre-built golden image in ~/.wasp/images/golden/.

Workspace stuck in “Starting”

The provisioner is trying to inject the SSH key via the serial console. This can hang if: - The base image doesn’t boot to a login prompt - The guest OS doesn’t have a root account - The disk image is corrupted

Check the serial console tab for clues. You may need to stop and delete the workspace, then try with a different image.

Terminal tab shows “Workspace Not Running”

Terminal tabs require a running workspace with a resolved IP address. Make sure: 1. The workspace is in the Running state (green dot) 2. The VM has booted completely (check the serial console)

SSH connection fails repeatedly

The terminal tab retries SSH connections automatically (up to 10 times). If it still fails: - The SSH daemon may not be running inside the guest. Check the serial console and run systemctl start sshd. - The SSH key may not have been provisioned correctly. Try stopping and restarting the workspace.

Port forward not working

  • Make sure the workspace is running
  • Verify the service is actually listening on the guest port (ss -tlnp inside the VM)
  • Check that nothing else on your Mac is using the host port

“VZErrorDomain Code=2” crash on start

This usually means the entitlements file is missing the virtualization key. Verify:

grep "com.apple.security.virtualization" Resources/wasp.entitlements
grep "com.apple.security.virtualization" Resources/wasp-dev.entitlements

Both should contain com.apple.security.virtualization. If not, the entitlements were accidentally overwritten. See AGENTS.md for the fix.
