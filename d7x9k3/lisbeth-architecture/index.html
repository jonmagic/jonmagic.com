Lisbeth Architecture

System Overview

Lisbeth is a conversational AI agent with three client surfaces:

  1. iOS app — multi-modal conversation client (text + voice) using SFSpeechRecognizer and AVSpeechSynthesizer for voice I/O, with all LLM inference delegated to the server via SSE streaming.
  2. Slack — DMs, channel @mentions, and slash commands via Bolt v4 Socket Mode (WebSocket from NAS to Slack, no public URL needed).
  3. HTTP API — RESTful endpoints for tool execution, session management, cron, Gmail, Google Calendar, Google Maps, Spotify, and webhooks.

The server is an Express 5 app running on Bun, hosted in Docker on a Synology NAS. It provides cloud LLM inference via the GitHub Copilot SDK, tool execution, persistent memory, git repo access, Google integrations (Gmail, Calendar, Maps), Spotify integration, cron scheduling, and Slack integration.

All conversational queries — text, voice, or Slack messages — flow through the Copilot SDK for LLM reasoning. The iOS app and Slack handle their respective I/O; the server handles all inference and tool execution.

Key architectural decisions

Decision Rationale
Server as sole LLM All inference via Copilot SDK; eliminates on-device model dependency, enables richer tool use
Bun monorepo (shared/server/client) TypeScript across the stack; shared Zod schemas for type-safe validation
SQLite for all persistence Single lisbeth.db file via sql.js (WASM). Replaces the earlier patchwork of JSON/JSONL files
Markdown context files for memory Agent reads/writes context.md files via SDK tools — simpler and more flexible than a structured memory store
Copilot SDK via TCP socket (not stdio) Bun’s stdin pipe handling on Linux x64 causes premature EOF; TCP avoids this
Docker on Synology NAS + Tailscale Self-hosted, persistent, accessible from anywhere
No third-party deps in iOS app Swift 6.0 strict concurrency; Apple frameworks only
Code-as-tools pattern Reusable TypeScript templates in server/scripts/ that the agent reads, customizes, and executes via the SDK bash tool — avoids purpose-built tools for every operation
Slack via Socket Mode WebSocket from NAS to Slack — no public URL or ingress needed

Middleware chain (in order)

  1. requestIdMiddleware — assigns UUID to every request (server-generated, never accepts client-supplied)
  2. requestLoggingMiddleware — structured JSON request/response logging with request ID and duration
  3. createWebhookRoutes — mounted BEFORE express.json() (webhooks need raw body for HMAC verification)
  4. express.json({ limit: '20mb' }) — JSON body parsing
  5. authMiddleware — mounted at /v1 only. Bearer token with:
    • Dev bypass: disabled when LISBETH_API_TOKEN unset
    • Public path bypass: /oauth/spotify/callback, /oauth/gmail/callback, /oauth/calendar/callback, and /webhooks/github skip auth
    • Localhost bypass: 127.0.0.1 / ::1 / ::ffff:127.0.0.1 bypass auth
    • Constant-time token comparison via timingSafeEqual
  6. All route handlers
  7. errorHandlingMiddleware — catch-all 4-arg Express error handler (must be last). Returns { ok: false, error }. Hides internal messages for 5xx.

Startup sequence

  1. loadConfig() — validate env vars via Zod (fail fast)
  2. createApp(config) — create Express app, SQLite DB, all stores, CopilotManager, SlackApp, routes, middleware
  3. app.listen(port, '0.0.0.0') — start HTTP server
  4. After listening:
    • cronJobStore.ensureDefaults() — seed default cron jobs if table is empty
    • cronScheduler.start() — start 60-second tick loop
    • slackApp?.start() — start Slack Socket Mode connection
  5. registerShutdown(server, cleanupFn) — register graceful shutdown (stops Slack → cron → Copilot → DB)

Data Layer

SQLite database

All persistence uses a single SQLite database (data/lisbeth.db) via sql.js (WASM-based, in-memory with manual disk persistence).

Persistence model: The database runs in-memory. After every mutation, the entire DB is exported as a binary buffer and written to disk via fs.writeFileSync. Transactions defer persistence to commit.

Migration system: A schema_version table tracks applied migrations. Migrations are applied sequentially on startup.

Schema (Migration v1)

Table Primary Key Purpose
schema_version version INTEGER Tracks applied migration versions
messages id INTEGER AUTOINCREMENT Conversation message logs. Columns: conversation_id, data (JSON blob), created_at. Index on conversation_id.
sessions conversation_id TEXT Session summaries. Columns: started_at, ended_at, message_count, summary
cron_jobs id TEXT Cron job definitions. data column holds JSON blob.
cron_state job_id TEXT Per-job last run tracking. Columns: last_run, last_result
cron_history id INTEGER AUTOINCREMENT Append-only cron run history. Columns: job_id, data (JSON), created_at. Index on job_id.
memory key TEXT Key-value memory entries (vestigial — see Memory System). Columns: value, tags, created_at, updated_at
oauth_tokens provider TEXT Encrypted OAuth tokens. Single data TEXT column.
playlist_state id INTEGER CHECK (id = 1) Single-row JSON blob for playlist generator state

Memory system

Memory uses plain markdown context files, not a structured store:

  • Global context: data/memory/context.md — facts, preferences, knowledge injected into every session’s system prompt
  • Per-conversation context: data/<conversationId>/context.md — conversation-specific context

The agent reads and writes these files using SDK tools (view, edit, create). Content is loaded into the system prompt at session creation via buildMemoryContext().

The memory SQLite table exists (from migration v1) but is vestigial — the JsonMemoryStore and remember/recall tools that used it have been removed. Memory is now entirely agent-initiated via context files.

Limitation: Memory injected into the system prompt is a snapshot at session creation time. Changes during a conversation are not visible in the prompt until a new session is created.

Conversation history replay

When a session can’t be resumed from the SDK’s on-disk persistence, buildConversationHistory() reads the last 50 messages from SqliteMessageLog and formats them as User: ... / Lisbeth: ... turns, injecting them into the system prompt so the agent has conversational context.

Session Management

Session lifecycle

First message with new conversationId
    → pullRepos() (git pull --ff-only on all allowed repos)
    → getClient() (lazy CopilotClient singleton, TCP socket mode)
    → buildMemoryContext() (read context.md files)
    → buildConversationHistory() (last 50 messages from SQLite)
    → createToolsForConversation() (share, cron_list, cron_manage)
    → client.createSession({model, tools, skillDirectories, hooks, systemMessage})
    → cache in Map<convId, Session>

Subsequent messages to same conversationId
    → reuse cached session (has conversation history)

Cache miss (e.g., after server restart)
    → client.resumeSession(sessionId) restores session from SDK disk persistence
    → re-cached in Map<convId, Session>

Resume failure
    → create new session with history replay (buildConversationHistory)

DELETE /v1/conversations/:id
    → session.destroy() + cache eviction + SDK disk cleanup
    → delete session + messages from SQLite

Stale session recovery

If the Copilot SDK throws “Session not found” during a message, the session is evicted from cache and a fresh one is created transparently (single retry). Both the messages route and Slack handler implement this pattern.

Tool safety hooks

Pre-tool-use hook (runs before every SDK tool execution):

  • File tools (view, edit, create, glob, grep): validates all paths are within allowed directories (data/repos/brain, data/repos/home, data/repos/lisbeth, conversation workspace)
  • Bash: blocks dangerous patterns (fork bombs, rm -rf /, mkfs, dd, pipe-to-shell, chmod 777 /, shutdown, reboot). Rewrites commands with env -i to strip secrets — only safe env vars exposed (PATH, LANG, TERM, NODE_ENV, TZ, PORT, HOME, TMPDIR, USER, SHELL)

Post-tool-use hook: logs every tool invocation with tool name, result type, error, and result preview (first 200 chars).

parseToolArgs(): handles the Copilot SDK’s inconsistent argument passing (sometimes object, sometimes JSON string) by normalizing both forms.

Cron Scheduler

The cron scheduler gives Lisbeth autonomous behavior — running scheduled tasks without user prompting.

Components

  • SqliteCronStore (cron-store.ts) — job CRUD, state persistence, history in SQLite
  • CronScheduler (cron-scheduler.ts) — 60-second setInterval tick loop, evaluates cron expressions
  • CronMatcher (cron-matcher.ts) — 5-field cron expression parser/evaluator (no external deps)
  • AgentExecutor (cron.ts) — sends prompts to Copilot SDK on dedicated __cron__<jobId> conversations
  • ScriptExecutor (app.ts) — spawns bun -e <code> subprocesses for cron script-mode tasks

Job modes

  • Agent mode — sends a prompt through the Copilot SDK with full tool access
  • Script mode — runs TypeScript via bun -e in a subprocess

Default jobs (seeded if table is empty)

Job Schedule Mode Description
health-check */5 * * * * script Hits /health, reports status
disk-usage */5 * * * * script Calculates data dir size

Slack notifications

Jobs can optionally notify Slack after execution. The CronJobSchema includes slackChannel (channel ID) and slackNotify ('always' | 'error' | 'never') fields. The scheduler uses the postToSlack() function exported from slack.ts.

Slack Integration

Architecture

Slack is a first-class client alongside the HTTP API and iOS app. Uses Socket Mode (WebSocket from NAS to Slack) so no public URL is needed. Built with @slack/bolt v4, running inside the existing server process.

Module: server/src/slack.ts — createSlackApp() returns a SlackApp or null if tokens aren’t configured.

Surfaces and triggers

Surface Trigger Behavior

Thread-based conversation IDs

  • DM: slack-dm-{userId}-{threadTs} (dots replaced with dashes)
  • Channel: slack-ch-{channelId}-{threadTs}

File attachment handling

  • Text files (text/*, application/json, etc.): downloaded and inlined as code blocks in the prompt
  • Images (image/*): downloaded to workspace directory, passed as SDK file attachments for vision
  • Other files: noted with filename and type but not processed
  • Max file size: 1MB

UX details

  • Adds :thinking_face: reaction while processing, removes when done
  • Messages exceeding 3900 chars are split at paragraph boundaries
  • Custom redirect-following download logic for Slack’s cross-origin CDN URLs

Voice Pipeline State Machine

States

State Description Mic TTS LLM
idle Pipeline inactive, not started OFF OFF OFF
listening Mic on, STT transcribing, silence timer running ON OFF OFF
processing User speech committed, LLM streaming response OFF OFF ON
speaking TTS playing sentence chunks from LLM output OFF ON may still be ON
error Recoverable error (e.g., STT failed after 5 retries) OFF OFF OFF

Transitions

From To Trigger
idle listening start()
listening processing handleEndOfSpeech() — silence timer (1.5s) or isFinal=true
processing speaking speak(sentence) — LLM text chunks accumulated into sentence buffer
speaking listening checkTurnComplete() — llmStreamDone && !synthesizer.isSpeaking
speaking listening interrupt() — user taps screen
processing listening interrupt() — user taps screen
any active idle stop()
listening error STT error after 5 retries with exponential backoff
processing listening LLM error → restart listening (not error state)

Critical coordination mechanisms

Producer-consumer turn completion: The LLM (producer) and TTS (consumer) both call checkTurnComplete() when they finish. Only when BOTH llmStreamDone == true AND !synthesizer.isSpeaking does the pipeline restart listening. This eliminates the race condition where TTS finishes between speak() and the LLM task completion.

Generation counter: listeningGeneration is a monotonically increasing counter incremented on every intentional state change. All STT callbacks and backoff restarts capture the generation at creation time and check it before acting. Stale callbacks are discarded, breaking restart loops.

Silence detection: Only bumps lastSpeechTime when the transcript text actually changes (transcript != self.userTranscript). STT fires many partial results with updated confidence but unchanged text — these must NOT reset the silence timer.

Critical constraint: SFSpeechRecognizer and AVSpeechSynthesizer cannot run simultaneously — the mic picks up speaker output creating a feedback loop. The mic is always OFF during TTS.

Post-turn invariants

After every complete turn (pipeline returns to listening):

  1. userTranscript == ""
  2. isProcessingSpeech == false
  3. sentenceBuffer == ""
  4. llmTask == nil
  5. state == .listening

Data Flow

Text query (iOS)

  1. User types message in composer → taps send
  2. ConversationViewModel calls ServerStreamingService.streamMessage()
  3. APIClient.streamMessage() → POST /v1/message/stream (SSE)
  4. Server creates/resumes Copilot SDK session
  5. Cloud LLM may invoke tools (bash, view, edit, create, glob, grep, share_conversation, cron_, repo_)
  6. Server streams text_delta events back as SSE
  7. Each chunk appended to agent message in real-time
  8. SSE done event → server logs to SQLite

Voice query (iOS)

  1. User speaks → SFSpeechRecognizer transcribes to text
  2. Silence detected (1.5s) → handleEndOfSpeech()
  3. Pipeline sends prompt via ServerStreamingProtocol.streamMessage()
  4. Same SSE flow as text query (steps 3–8 above)
  5. Each chunk also routed to AVSpeechSynthesizer for spoken output
  6. checkTurnComplete() → restart listening

Slack query

  1. User sends DM, @mentions in channel, or replies in tracked thread
  2. Slack Socket Mode delivers event to slack.ts
  3. Handler adds :thinking_face: reaction, downloads any file attachments
  4. Sends prompt to CopilotManager.sendMessage() (same Copilot SDK path)
  5. Response split at paragraph boundaries if >3900 chars
  6. Reply posted to thread, :thinking_face: removed

Interrupt flow (iOS)

  1. User taps screen during speaking/processing
  2. interrupt() → stop TTS, cancel LLM task, set llmStreamDone = true
  3. Restart listening immediately

Spotify & Playlist Integration

OAuth flow

  1. Agent or user triggers Spotify connection → GET /v1/oauth/spotify/authorize
  2. Redirects to Spotify’s authorization page with configured scopes
  3. Spotify redirects back to GET /v1/oauth/spotify/callback with auth code
  4. Server exchanges code for access + refresh tokens
  5. Tokens encrypted with AES-256-GCM via SqliteOAuthStore and persisted to SQLite
  6. SpotifyClient auto-refreshes expired tokens using the refresh token

  • CSRF protection via cryptographically random state parameter with 10-minute TTL
  • Single-use state tokens (deleted on consumption)
  • Callback endpoint is publicly accessible (browser redirect); all other OAuth endpoints require auth

Playlist generator

The playlist generator maintains persistent state in the playlist_state SQLite table:

  • Taste profile — genre preferences, energy levels, vibe descriptors
  • Playlist history — previously generated playlists with track lists
  • Discovered artists — curated artist database with scores and tags
  • Discovery run state — progress tracking for artist discovery sessions

The agent uses server/scripts/playlist.ts and server/scripts/spotify.ts templates to build playlists via the code-as-tools pattern.

Google Integrations

Gmail and Calendar OAuth model

Gmail and Google Calendar share the same Google OAuth foundation:

  1. Agent or user triggers GET /v1/oauth/gmail/authorize or GET /v1/oauth/calendar/authorize
  2. Google redirects back to the matching callback with an authorization code
  3. routes/oauth.ts exchanges the code for access + refresh tokens and stores them in SqliteOAuthStore
  4. google-token.ts refreshes expired Google access tokens for both services
  5. gmail-client.ts and google-calendar-client.ts use the refreshed access token to call Google APIs

This keeps Gmail and Calendar aligned on security and storage:

  • Shared CSRF-protected OAuth state handling in routes/oauth.ts
  • Encrypted token storage in SQLite via SqliteOAuthStore
  • Shared token refresh logic in google-token.ts
  • Public callback endpoints, with all other OAuth admin routes still protected by bearer auth

Gmail API surface

gmail-client.ts and routes/gmail.ts expose a read-focused Gmail proxy for:

  • profile lookup
  • label listing
  • message search with Gmail query syntax
  • message detail retrieval with decoded text/plain bodies

Calendar API surface

google-calendar-client.ts and routes/calendar.ts expose Google Calendar operations for:

  • listing accessible calendars
  • listing events in a time window
  • retrieving a single event
  • creating a new calendar event

The agent-facing server/scripts/calendar.ts template supports the same flows and defaults to safer personal-use behavior. Attendees remain opt-in so testing or casual event creation does not notify other people unless explicitly requested.

Maps API-key model

Google Maps uses server-side infrastructure credentials rather than per-user OAuth:

  • GOOGLE_MAPS_API_KEY enables the integration
  • google-maps-client.ts calls the Geocoding API, Places API (New), and Routes API
  • routes/maps.ts normalizes responses into Lisbeth-friendly JSON for geocoding, place search, and route lookup
  • Google API error details are preserved so operators can distinguish misconfiguration from code issues

Production verification uses scripts/test-maps-production.sh, which safely performs read-only lookups and now treats disabled Google Cloud APIs as SKIP instead of a hard failure.

Auto-update behavior

The auto-update script (deploy/auto-update.sh) runs every minute via cron:

  1. Log rotation — truncates auto-update.log if >100 KB
  2. Concurrency lock — PID file with 10-minute stale lock timeout
  3. Git fetch & compare — exits silently if already up-to-date
  4. Skip check — .auto-update-skip file prevents retrying known-bad commits
  5. Clean & pull — git checkout -- . && git clean -fd, then git pull --ff-only
  6. Infrastructure vs. source-only detection:
    • Infrastructure changed (package.json, bun.lock, Dockerfile, docker-compose.yml): full docker build + docker-compose up -d
    • Source-only changed: fast docker restart lisbeth (bind mounts pick up changes)
  7. Health check — polls /health every 5s for up to 60s
  8. Auto-rollback — on build failure or health check failure, rolls back to previous commit, writes skip file, rebuilds/restarts
